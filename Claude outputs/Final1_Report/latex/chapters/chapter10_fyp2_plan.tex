\section{Remaining Scope}
The remaining work has three parts:
\begin{enumerate}
    \item \textbf{Rest of Final-1 (before the Final-1 evaluation):} player model MLP1, calibrated simulator, PPO retrain on it, Policy SHAP, the BSP baseline, layout-diversity metrics and one evaluation script.
    \item \textbf{FYP-2 Mid (Week 26):} equipment shop, integration, non-functional benchmarks, release readiness; Judge retrained on real ratings.
    \item \textbf{FYP-2 Final (Week 32):} 10-participant counterbalanced user study, statistics, thesis and packaging.
\end{enumerate}

\section{Remaining Modules and Features}
\subsection{Rest of Final-1}
Implementation order (from the revised architecture, Section~\ref{sec:revised_arch}):
\begin{enumerate}
    \item \textbf{Data audit and schema (done):} 29 floors, 3 sessions, 1 player, all rated. Add a skill/$CR_0$ column if needed.
    \item \textbf{Player model MLP1:} dataset loader, grey-box model on top of simulator v3, split by player, MAE per output and a calibration check.
    \item \textbf{Judge (done offline):} connect it to the reward; retrain on real ratings when there are enough players.
    \item \textbf{Calibrated simulator:} a new environment that samples results from MLP1 and uses the Judge in the reward. Keep per-room pacing (it removed the room-count exploit). Keep simulator v3 for ablation.
    \item \textbf{Retrain PPO:} same contract; check latency and file size; re-run the sensitivity audit for new exploits.
    \item \textbf{Policy SHAP:} exact Shapley values over the 8 inputs on the actor; summary plot and per-decision attributions; optionally precomputed importances for the overlay.
    \item \textbf{BSP baseline and evaluation:} Section~\ref{sec:bsp_plan}; then one script that fills Table~\ref{tab:baseline_plan}.
\end{enumerate}

\subsection{In-Run Equipment Shop (FYP-2 Mid; moved from Final-1)}
Players earn currency (\textit{Forge Embers}) and buy weapons, armour and boots in shop rooms. The policy should notice the player's new power through telemetry and adjust. Doors and keys in chests, which tie into the same item system, are planned with it. This also adds the ``player powers'' the committee asked for.

\subsection{Judge on Real Data and In-Game Explanations (FYP-2 Mid)}
Collect a corpus of 25+ consented players, retrain the Judge on the rating target, refit the simulator's damage model to real outcomes, and port the trees and SHAP values to GDScript for a live explanation panel showing both Judge SHAP and Policy SHAP.

\section{Testing and Validation Plan}
\begin{itemize}
    \item \textbf{Final-1:} the comparison in Table~\ref{tab:baseline_plan} (solvability, pacing error, layout diversity, recovery after a skill change) for FORGE, static $+8\%$ and BSP, plus PPO on simulator v3 vs.\ PPO on the calibrated simulator (ablation). Pilot real-data checks for MLP1 and the Judge, reported with their $n$.
    \item \textbf{FYP-2 user study:} 10 participants stratified by gaming experience. Each plays three conditions in counterbalanced order: FORGE, static $+8\%$, and BSP. \tofill{decide which baseline is the primary comparison arm}. All conditions get the same five calibration floors, or floors 6+ are reported separately. Measures: per-floor 1--5 rating, GEQ and PENS per session (licence to be confirmed). Analysis: repeated-measures ANOVA with paired follow-ups and effect sizes. With 10 participants the power is low (about 29\% for a medium effect), so the study is exploratory.
    \item \textbf{Leakage:} players whose data trains the Judge or MLP1 should not be UAT participants where possible.
\end{itemize}

\section{Deployment Plan}
\begin{itemize}
    \item \textbf{Target:} a standalone Windows 64-bit build, exported from the \texttt{Windows Desktop} preset (playtest flavour). A first deployment has been made: playtest build 0.9.0 (\texttt{dist/FORGE.exe} with \texttt{FORGE.pck} and the godot-sqlite DLL), sent to testers with \texttt{PLAYTEST.md}.
    \item \textbf{Linux and Web:} only Windows presets exist today. A Web build would need the godot-sqlite WebAssembly path tested, so Linux and Web are ``nice to have'' for FYP-2.
    \item \textbf{Release process:} CI builds a PCK smoke test on every push; \texttt{release.yml} builds tagged releases (its Godot version must be updated to 4.7.2).
    \item \textbf{Rollback:} each release is a Git tag; if a new policy misbehaves, the previous \texttt{policy\_weights.json} is restored, and the heuristic fallback keeps the game playable in the worst case.
    \item \textbf{Handover:} README, \texttt{PLAYTEST.md}, results files and the implementation reference document.
\end{itemize}
