## Page 2 — Proposal Defence Details

### Proposal Defence Breakdown:
- **Weight:** 10% of FYP-1

### What to Bring:
- → Documentation (Proposal document)
- → SoW (Scope of Work) / PPT (Presentation slides)
- → Working Prototype / Demo

### Key Evaluation Areas:
- → **Literature Survey** — Research-backed problem understanding
- → **Problem Statement** — Clear, specific articulation
- → **Proposed Solution** — Technical approach
- → **Scope of Work** — Bounded deliverables
- → **Timeline** — Realistic milestones
- → **Technology Stack** — Justified choices

### Important Notes:
- Panel looks for **technical depth**, not just UI demos
- Must show **feasibility evidence** (POC / spike)
- The **demo should work** — not be a static mockup

## Page 3 — Mid Evaluation Details

### Mid Evaluation Focus:
- **SRS** (Software Requirements Specification) — must be approved
- **SDS** (Software Design Specification) — must be baselined
- → Requirements should be **uniquely identified, testable, and prioritized**
- → At least **one measurable non-functional requirement** per quality attribute

### Design Baseline Requirements:
- → Component diagrams
- → Data design
- → Interface specifications
- → Security considerations
- → Deployment topology
- → Failure handling

### Critical Point:
- → **Traceability matrix** must be opened
- → API and third-party dependency register started

---

## Page 4 — Final Evaluation (FYP-1)

### Core Build Requirements:
- → **Working core system** covering primary scenario end-to-end
- → Built against the **approved design**
- → Integration path **proven rather than assumed**
- → Comparison baseline measured
- → Deployment target selected and **first deployment attempted**

### Documentation State:
- → Traceability matrix populated for all committed requirements
- → Requirement → Design → Test coverage mapping
- → Test, deployment, rollback and handover plan drafted
- → Timeline revised against actual progress
- → Scope changes processed under change control

---

## Page 5 — FYP-2 Expectations

### Mid-2 (Gate 4 — Release Readiness):
- → All committed scope implemented and integrated
- → System testing complete
- → Non-functional criteria **measured against stated targets** (not asserted)
- → Evaluation running against baseline
- → Failure and edge cases exercised deliberately
- → No open Critical defects; every open High defect with approved disposition

### Final-2 (Gate 5 — Final Acceptance):
- → Deployable, documented system installed and operated in target environment
- → Acceptance testing completed with supervisor or client
- → Completed evaluation with results, limitations, and failure analysis
- → Every member able to **defend their technical ownership**

## Page 6 — Documentation Standards

### Required Documents:
1. Project Proposal and Initiation Plan
2. Scope of Work (with named approver)
3. Software Requirements Specification (SRS)
4. Software Design Specification (SDS)
5. Requirements Traceability and Acceptance Matrix
6. Test, Deployment and Handover Plan
7. Final Project Report (Thesis)

### Document Control:
- Every document carries: **version, date, author, status**
- Documents progress: **Draft → Review → Approved Baseline**
- Groups should **version their documents rather than overwrite**
- Panel should be able to see how requirements and design **evolved** across semesters

## Page 7 — Important Reminders

### AI Usage Policy:
- → Development at **Level 2: AI-Assisted Development**
- → Human students maintain **complete design authority and technical ownership**
- → AI used only for localized assistance (refactoring, syntax, boilerplate)
- → Must pass **4 tests of understanding** on all code:
  1. Explain functionality without reading code
  2. Justify architectural decisions against alternatives
  3. Predict failure modes under stress
  4. Modify code live under panel questioning
- → **AI usage log** required in repository (`AI Logs/` directory)

### Ethical Considerations:
- → Games with adaptive difficulty have ethical implications (player manipulation, dark patterns)
- → Must be briefly acknowledged in proposal

### General Advice:
- → **Don't overclaim** — Panel values honesty over ambition
- → **Show what's real** — clearly separate implemented from planned
- → **Be specific** — avoid vague terms like "smart", "AI-powered", "innovative"
- → **Know your code** — every member must be able to explain and modify every part
